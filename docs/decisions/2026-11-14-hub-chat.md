# Hub chat

## Context

`002-schema.sql` has had `hub_messages` since the start: a flat chat with an optional quote of
one earlier message, messages up to 10,000 characters, soft delete, and triggers that let only
active members of an active hub post and that set `edited_at`. Brainstorm notes were given their
own table so the chat stayed free (`2026-11-14-hub-brainstorm-notes.md`). No route used it.
Tracker rows 51 to 54 ask for reading, sending, editing and deleting. The build plan keeps the
hub's tools to small lists with no WebSockets or Redis.

## Decision

- Four routes under `/v1/hubs/{hub_id}/messages`, for active members only, in every phase. The
  team does not have to be confirmed: people who just joined need to talk before it is.
- Newest first, paged with `offset` and `limit` like the other lists. No live updates: the page
  loads the chat again (a Refresh button or a reload). Changed on 2026-11-15: a WebSocket now
  pushes changes live (`2026-11-15-live-hub-chat.md`).
- A reply carries the quoted message's author and text, or `null` text once that message is
  deleted.
- Only the author edits. The author or the hub's owner deletes, as with notes.
- An archived hub's chat is read only.
- The database triggers stay the final check: a message from someone removed a moment earlier
  is refused there and answers `409 HUB_CHANGED`.

## Options we considered

- Live chat over WebSockets. Not chosen: the API runs as one process with in-memory state and
  has no pub-sub, and the landing page does not claim live chat.
- Keyset paging on (created_at, id). Not chosen for now: every other list pages by offset, and a
  hub has at most five people. Revisit if a busy hub's pages repeat messages.
- Let the owner edit any message. Not chosen: an edit changes what someone said under their name.

## Consequences

New messages appear only when the page loads the chat again. A message posted while someone
reads page two can shift that page by one. The web side is still to build.
